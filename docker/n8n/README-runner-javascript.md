# Entradas del runner JavaScript de n8n 2.46.6

El runner es `@n8n/task-runner` 2.46.5 dentro del release n8n 2.46.6. Su entrada es `dist/start.js`. El preparador toma el código y los manifests del TAR fijado en el inventario de remediación y conserva la topología de workspaces y los snapshots con peers del lock original. [Paquete del runner](https://github.com/n8n-io/n8n/blob/bb72d756104542adb549b6966a57e21459bd52a2/packages/%40n8n/task-runner/package.json) · [Configuración de runners](https://github.com/n8n-io/n8n/blob/bb72d756104542adb549b6966a57e21459bd52a2/docker/images/runners/n8n-task-runners.json)

```powershell
python -B docker/n8n/stage_runner_javascript.py --archive <tar-original> --output <contexto-nuevo>
```

La salida incluye 19 proyectos de ejecución y 29 al incluir construcción. Los artefactos enumerados son 452 y 1.720 respectivamente, incluidos opcionales para otras plataformas. El preparador exige SRI SHA-512 y la URL canónica del registro para cada paquete alcanzable. Conserva byte a byte el documento bootstrap de pnpm 12.4.2 y proyecta el segundo documento del lock al cierre comprobado. Se conserva el código fuente original y se añade `moment@2.30.1` al manifiesto del runner, como fija el Dockerfile upstream. Las resoluciones `follow-redirects` 1.16.1 y `undici` 7.29.1 pasan a 1.16.2 y 7.30.1. El peer opcional `debug` conserva su identidad y snapshots. Los ocho patches alcanzables se toman del TAR, incluidos los cuatro de ejecución `@lezer/highlight`, `assert`, `lodash` y `xml2js`. [Metadatos de Moment](https://registry.npmjs.org/moment/2.30.1) · [Follow Redirects](https://registry.npmjs.org/follow-redirects/1.16.2) · [Undici](https://registry.npmjs.org/undici/7.30.1)

## Resultado de la resolución aislada

La entrada V3 está en `.tools/n8n-remediation/runner-javascript-build-v3`. El SHA-256 de `SHA256SUMS` es `243172decbb021c06c9c339b9f276cb369be4e25be7f781d9bd952127373358d`. El lock derivado tiene SHA-256 `9acd3ea5797eafc627a0b160fe928248b0381e2b051a404b09e0adbc210c8cf7`. La versión nativa Windows de pnpm 12.4.2 se comprobó por SRI del bootstrap y se ejecutó con caché nueva, `--offline --frozen-lockfile --lockfile-only --ignore-scripts`, entorno explícito y `PATH` vacío. Leyó los dos documentos, seleccionó 29 de 30 importers e inició el control de suministro sobre 1.720 entradas. Conservó los 40 archivos de entrada de la prueba.

El control terminó con `ERR_PNPM_NO_OFFLINE_META` en `@aashutoshrathi/word-wrap`. La caché de metadatos del registro estaba vacía. El recibo está en `.tools/backup-source-build/n8n-js-frozen-lock-v3/receipt.json` con SHA-256 `45ac1d3640d058382ad114561b73bb8747501778f5c3cea87ce786b6dbb4c406`. Se conserva la revisión anterior que falló el framing de YAML y la preimagen que contenía una resolución ajena al runner. [Modo offline y lock congelado de pnpm](https://pnpm.io/cli/install)

Validar los bytes por SRI y volver a pasar la prueba `--offline --frozen-lockfile --lockfile-only --ignore-scripts` con esa caché. Instalar el cierre en Linux con el store acreditado y `--offline --frozen-lockfile --ignore-scripts`. Mantener deshabilitados `pnpmfile`, cambios de versión del gestor y lock de rama. Usar el binario absoluto de pnpm fijado, entorno sin credenciales y un `PATH` acotado sin Git.
2. Usar Node 26.12.1 en Linux amd64 musl, como fija el Dockerfile original. El ABI del módulo de Node es 147. El tarball de `isolated-vm` 7.0.1 contiene `isolated-vm.abi147.musl.node` autenticado por el SRI del lock. Su SHA-256 es `41dd9d63868631c534066b4626bb818f59a4fc7c1d58ff33b9e759c49feb8cb9`. La receta debe verificar con Node su carga y la de los demás módulos nativos utilizados, con scripts de instalación deshabilitados. [ABI de Node 26.12.1](https://github.com/nodejs/node/blob/v26.12.1/src/node_version.h) · [Metadatos de isolated-vm](https://registry.npmjs.org/isolated-vm/7.0.1)

Comprobar `dist/start.js`, los enlaces internos y el inventario resultante antes de copiar a `/opt/runners/task-runner-javascript`. `moment` ya tiene pin en la entrada.
