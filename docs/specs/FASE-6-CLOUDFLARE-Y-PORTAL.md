# Fase 6 · Cloudflare Edge y portal audiovisual

El portal de E-scale Studio se construye con Next.js y se sirve desde Pages en `studio.e-scale.cl`. Una función de Pages entrega las rutas `/api/*` del dominio al Worker `studio-api-worker` mediante un binding de servicio. El Worker usa D1, KV, el bucket privado de media y la cola de trabajos. El dominio `workers.dev` está deshabilitado. [Bindings de Pages](https://developers.cloudflare.com/pages/functions/bindings/#service-bindings)

## Identidad y planes

- `/api/auth/google` genera `state`, `nonce` y un desafío PKCE S256. Su callback contrasta el estado de la sesión. Después canjea el código y solicita en paralelo las claves públicas de Google. Si el canje falla, cancela la consulta de claves. Sólo después de comprobar los campos y la firma del token, el portal registra la identidad interna y entrega una cookie protegida de ocho horas. El cierre revoca la sesión verificable en D1 y limpia la entrada auxiliar de KV. [OAuth para aplicaciones web de Google](https://developers.google.com/identity/protocols/oauth2/web-server)
- `GET /api/dashboard` carga la identidad, el plan, los pedidos y las entregas iniciales. El Worker verifica una vez la sesión en D1 y lee en paralelo los recursos del titular para el entorno activo. La respuesta usa `Cache-Control: no-store`. Si se revierte a un Worker anterior que carece de esta ruta, el portal carga los mismos datos desde las rutas individuales.
- D1 decide la cuota del mes y serializa la reserva de producción y la anotación en el ledger. El cliente reutiliza la clave de idempotencia para el mismo pedido. Free admite 1 producción al mes, Pro 12, Ultra 40 e Ilimitado carece de tope mensual. El valor comercial de duración máxima sigue pendiente. [Esquema de cuotas](../../cloudflare-saas/migrations/0001_schema.sql)
- La aplicación usa Mercado Pago Suscripciones de Chile en modo de prueba. El perfil gratuito puede iniciar sesión sin checkout. El pago habilita una suscripción cuando el Worker coteja el mandato y el cobro de la misma aplicación. La URL de notificaciones de prueba es `https://studio.e-scale.cl/api/billing/webhook`. [Contrato de pagos](MERCADOPAGO-FASE-6.md)

## Ingesta y entregas

- El navegador calcula SHA256 antes de subir las partes directamente a R2. El Worker proporciona firmas de alcance limitado, coteja `ListParts`, valida tamaño y SHA256 del objeto completo y registra el trabajo en D1. El backend NAS recibe una orden firmada, con reintento y cola de fallos. [Contrato de ingesta](../../cloudflare-saas/studio-api-worker/INGESTA.md)
- El chat solo admite órdenes propias con carga comprobada. El Worker firma y coteja la solicitud y respuesta del intermediario de Sofía. El piloto está restringido a la cuenta corporativa de Jorge en el plan Free de prueba. Usa el OAuth de Codex que ya gestiona OpenClaw para el agente `agency-account`. El complemento accede al runtime aislado por un socket privado y exige el modelo `gpt-6.1-terra`. La publicación requiere el transporte autenticado desde el WAF. [Intermediario de Sofía](../../openclaw-agency-setup/sofia-broker/README.md) · [Ingreso del NAS](../../ingress/README.md)
- La Sala de Entrega autentica al dueño del pedido. D1 registra versiones y SHA256 de ZIP privados, y el Worker transmite la versión acreditada desde R2. [Contrato de entrega](ENTREGAS-FASE-6.md)

## Despliegue y comprobación

1. Ejecutar `npm ci --ignore-scripts --prefix cloudflare-saas/studio-portal-web`, `npm run build --prefix cloudflare-saas/studio-portal-web` y `npm test`. Compilar la entrada modular del Worker con esbuild. Mantener la configuración `wrangler.example.jsonc` como ejemplo local y leer las identidades reales desde la bóveda.
2. Aplicar las migraciones ordenadas con la API D1. Si se actúa sobre la base existente, comprobar el propietario, las migraciones ya aplicadas y el esquema antes de ejecutar el SQL siguiente. Cotejar el esquema y las cuotas después. El flujo REST registra los SHA256 y los recibos de aplicación fuera de la tabla local de Wrangler.
3. Cargar el Worker por API de scripts con los cuatro bindings y los secretos ya respaldados. Configurar el servicio `STUDIO_API` en Pages. Cargar el export estático, `pages-worker.js` como `_worker.js` y `pages-routes.json` como `_routes.json`. La vista previa permite verificar la ruta de salud y rechaza el inicio de sesión. [Carga directa de Pages](https://developers.cloudflare.com/api/resources/pages/subresources/projects/subresources/deployments/methods/create/)
4. Verificar la vista previa y publicar la rama de producción de Pages. Respaldar el registro DNS anterior y confirmar su propiedad antes de vincular el dominio final. Comprobar TLS, interfaz, `/api/healthz`, rechazo de sesión ausente y retorno de OAuth. La validación real añade una carga multipart, una orden con cuota agotada, el checkout de prueba, una notificación firmada del proveedor y la aprobación del ingreso del NAS.

El 14 de noviembre Cloudflare sirvió la vista previa con la API privada y confirmó D1, R2 y KV. Se cambió el CNAME de `studio.e-scale.cl` de un túnel sin conexión a Pages después de guardar su preimagen. La raíz y la sonda de salud devolvieron 200, y Google mostró la ruta de inicio de sesión. La aceptación operativa se mantiene en [ESTADO.md](../../ESTADO.md#verificación-de-fase-6).
